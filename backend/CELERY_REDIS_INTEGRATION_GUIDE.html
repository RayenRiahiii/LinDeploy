Architecture and Operations

Celery and Redis in LinDeploy

This guide explains why LinDeploy executes Ansible asynchronously, how Redis and Celery participate in an installation, how progress and cancellation work, and how to operate and troubleshoot the background execution layer.

Last aligned with source code: 2026-08-07.

1. Why This Layer Exists

Kubernetes and K3s workflows can run for several minutes. Running them directly inside an HTTP request would keep the Django request open, expose it to proxy timeouts, and prevent reliable progress monitoring or cancellation. LinDeploy therefore stores the request in the database and delegates execution to a Celery worker.

Django API

Validates input, creates execution records, queues work, and exposes status endpoints.

Redis

Transports queued tasks and stores Celery task results. It is not the permanent installation history.

Celery Worker

Runs the orchestration service outside the HTTP process and publishes live progress metadata.

Database

Remains the durable source of truth for installation status, targets, logs, timings, and history.

4. Configuration

Celery and Redis endpoints are environment-driven. They are not hardcoded in the current implementation.

CELERY_BROKER_URL=redis://127.0.0.1:6379/0
CELERY_RESULT_BACKEND=redis://127.0.0.1:6379/0
ANSIBLE_RUNNER_BACKEND=linux
ANSIBLE_REPO_ROOT=/absolute/path/to/backend/Playbooks

Use ANSIBLE_RUNNER_BACKEND=wsl on a Windows controller that delegates Ansible to WSL. Use linux when Django and the worker run natively on Linux.

Redis must not be exposed to untrusted networks. Bind it to localhost or a protected private network, enforce firewall rules, and use authentication/TLS when Redis is remote.

5. Task and Domain States

Celery state and LinDeploy installation state answer different questions.

LayerExamplesMeaning
CeleryPENDING, PROGRESS, SUCCESS, FAILURE, REVOKEDState of the background Python task.
Installation statuspending, running, success, partial_success, failed, cancelledBusiness result shown to the operator.
Installation phasequeued, ssh_check, running_playbook, finalizing, completed, failed, cancelledCurrent step in the LinDeploy workflow.
A Celery task can finish successfully as Python code while the Ansible business result is failed or partial_success. The database installation status is the authoritative value for the user interface.

6. Launch Lifecycle

  1. The frontend submits the installer template and selected host identifiers.
  2. Django validates that the template and hosts exist and are enabled.
  3. Django creates one Installation and one InstallationTarget per selected host.
  4. The API queues run_installation_task.delay(installation.id) and stores the task identifier.
  5. The worker reloads the installation from the database and calls the execution service.
  6. The service performs connectivity and compatibility checks, builds a temporary inventory, and launches Ansible.
  7. Live output updates progress, phase, current play, role, task, elapsed time, and task profiling data.
  8. The final recap is parsed per host and persisted in each InstallationTarget.
  9. The global result is calculated and the temporary execution files are removed.

7. Multi-Target Result Aggregation

A failed or unreachable target does not invalidate every reachable target. LinDeploy records the outcome independently and continues on eligible machines.

Target outcomesGlobal result
Every selected target succeeds.success
At least one succeeds and at least one fails, is unreachable, or is ineligible.partial_success
No target succeeds.failed
The operator cancels the active execution.cancelled

Per-target output is retained so the result modal can explain which clusters were created, which targets failed, and what action is recommended for each machine.

8. Progress Monitoring

The worker streams Ansible output and extracts structured progress. The frontend polls GET /api/installations/{id}/ and renders operator-facing information rather than Redis or Celery internals.

  • Current operation: installation, reset, cleanup, or full uninstall.
  • Current play, role, and task.
  • Observed and completed task counts.
  • Progress percentage and elapsed duration.
  • Per-target state and final diagnostics.
  • Task profile and bottleneck hints after completion.

Progress is an operational estimate based on observed Ansible events. It should not be interpreted as a guaranteed remaining-time calculation.

9. Cancellation

The cancellation endpoint marks the request as cancelled, revokes the Celery task, and asks the runner to terminate the Ansible process tree. This is necessary because revoking a Celery task alone does not guarantee that a child ansible-playbook process has stopped. 

POST /api/installations/{id}/cancel/
Cancellation cannot roll back remote changes already applied by completed Ansible tasks. The operator must use the matching reset or cleanup workflow when a cancelled installation leaves a partial cluster state.

10. Starting the Services

Redis health

redis-cli ping

Django

python manage.py migrate
python manage.py runserver 0.0.0.0:8000

Celery on Linux

celery -A backend worker --loglevel=info

Celery on Windows development environments

celery -A backend worker --loglevel=info --pool=solo

The Windows solo pool is suitable for local development. A Linux worker with the normal prefork pool and managed services is preferred for production.

11. Healthy-System Checks

# Django configuration
python manage.py check

# Worker registration and availability
celery -A backend inspect ping
celery -A backend inspect registered

# Redis
redis-cli ping

The worker registration output should contain auto_K8S.tasks.run_installation_task.

A healthy launch returns immediately from the API with an installation identifier, changes from pending to running, exposes live task information, and eventually reaches a terminal domain status.

13. Reliability and Security Rules

  • Keep the API, Redis, database, worker, and Ansible controller on trusted management networks.
  • Do not display generated inventories because they can contain SSH and privilege-escalation secrets.
  • Use restricted filesystem permissions for temporary inventories and remove them after execution.
  • Do not treat Redis as the permanent history; persist user-visible state in the database.
  • Use one worker identity with only the filesystem and process permissions needed to run LinDeploy.
  • Back up the database and protect environment files from source control.
  • Use SSH keys and host-key verification for production targets.
  • Apply cleanup workflows explicitly; never infer destructive cleanup from a transient execution error.

14. Production Deployment Recommendations

  • Run Django and Celery as managed Linux services or containers with restart policies.
  • Use a dedicated Redis service with persistence policy, authentication, monitoring, and backups appropriate to the environment.
  • Place Django behind a production HTTP server and reverse proxy; do not use runserver.
  • Collect Django, Celery, Redis, and Ansible runner logs centrally.
  • Add metrics for queue depth, execution duration, failure rate, stale runs, and worker availability.
  • Add a per-host execution lock before allowing multiple operators or concurrent jobs at enterprise scale.
  • Use separate queues when OpenShift workloads are introduced because their execution time and resource profile differ from K3s and Kubernetes.

15. Current Limitations

  • No authentication or role-based access control is currently enforced by the application.
  • Stored target credentials are not yet encrypted at the application level.
  • The current Installation.inventory_content field can retain generated inventory content containing credentials and must be removed, encrypted, or replaced by a redacted snapshot before production use.
  • Development environments may disable strict SSH host-key verification.
  • There is no global per-host lock preventing two installations from targeting the same machine simultaneously.
  • Unexpected worker termination can leave a stale running record that requires reconciliation.
  • Windows solo workers execute one task at a time and are not the recommended production topology.

These boundaries must be stated honestly when presenting LinDeploy as a workshop/lab platform versus a hardened enterprise service.

16. Presentation and Defense FAQ

Why not run Ansible directly in the Django request?

Long HTTP requests are fragile. Celery provides durable queuing, worker isolation, status tracking, progress reporting, and cancellation support.

Why use Redis?

Redis is a fast message broker supported by Celery. It transports tasks from Django to workers and stores Celery result metadata.

Is Redis the source of truth?

No. The relational database is the durable business source of truth. Redis is execution infrastructure.

What happens if one selected target is unreachable?

The target receives its own failed or unreachable result. Other eligible targets continue, and the global result becomes partial_success when at least one succeeds.

How does the user follow an installation?

The frontend polls the installation detail endpoint. Django returns the normalized phase, progress, current Ansible task, timings, and per-target results stored by the worker.

Does cancellation undo the installation?

No. It stops future execution as safely as possible. Already applied remote changes require the matching reset or full cleanup workflow.

Why keep tasks.py small?

A thin task wrapper separates queue concerns from orchestration logic, which improves testability and allows the same service code to be invoked outside Celery.

Does LinDeploy require WSL?

No. The runner is configurable. Native Linux is the preferred production controller, while WSL supports the current Windows development workflow.

How will this support OpenShift?

The same queue and status model can orchestrate longer OpenShift SNO stages. Dedicated queues, stronger locking, artifact storage, and resumable phases should be added for that workload.

What is the most important next hardening step?

Add authentication/RBAC, encrypted credential storage, strict SSH trust management, and per-host concurrency locks before production multi-user use.

17. Operational Summary

  • Django accepts and validates the request.
  • Redis carries the queued Celery message.
  • The Celery worker executes the LinDeploy orchestration service.
  • The selected runner launches Ansible on Linux or through WSL.
  • The database stores durable global and per-target results.
  • The frontend displays normalized operational status without exposing backend secrets.
