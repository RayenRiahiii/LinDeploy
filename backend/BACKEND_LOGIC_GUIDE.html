1. Purpose and Scope

LinDeploy is a web orchestration platform. It stores target and credential information, validates SSH access, generates temporary Ansible input, queues long-running work, executes installer or cleanup playbooks, and returns a result for every selected target.

Implemented

  • Kubernetes single-node with kubeadm, containerd, and Calico.
  • K3s single-node installation.
  • Kubernetes reset and full uninstall.
  • K3s cleanup and uninstall.
  • SSH prechecks, cancellation, history, progress, and per-host diagnostics.

Important topology rule

Selecting several hosts does not create one shared multi-node cluster. LinDeploy currently creates one independent single-node cluster on each selected host.

Not implemented yet

  • Shared multi-node or HA clusters.
  • OpenShift SNO provisioning.
  • Local artifact and image mirror.
  • Authentication, RBAC, and encrypted secret storage.

5. Configuration and Environment

Runtime configuration is loaded from backend/.env. The committed template is backend/.env.example.

DJANGO_SECRET_KEY=replace-me
DJANGO_DEBUG=False
DJANGO_ALLOWED_HOSTS=lindeploy.example.local
USE_SQLITE=False
DB_NAME=lindeploy
DB_USER=lindeploy
DB_PASSWORD=replace-me
DB_HOST=localhost
DB_PORT=5432
CELERY_BROKER_URL=redis://localhost:6379/0
CELERY_RESULT_BACKEND=redis://localhost:6379/0
ANSIBLE_RUNNER_BACKEND=linux
ANSIBLE_REPO_ROOT=
ANSIBLE_TIMEOUT=15
ANSIBLE_HOST_KEY_CHECKING=True
  • ANSIBLE_RUNNER_BACKEND accepts linux or wsl.
  • ANSIBLE_REPO_ROOT overrides the embedded Playbooks directory when required.
  • CELERY_BROKER_URL and CELERY_RESULT_BACKEND are environment driven, not hardcoded.
  • The permissive local defaults in .env.example must be hardened before production use.

8. Complete Execution Flow

  1. The frontend submits the system, template, selected host IDs, cluster configuration, and host overrides.
  2. Django validates enabled hosts, credentials, system type, playbook path, and normalized values.
  3. Kubernetes auto mode can inspect baseline state to avoid unsafe reinitialization.
  4. Django creates one Installation and one InstallationTarget per selected host.
  5. run_installation_task.delay(installation.id) queues the job in Redis.
  6. The Celery worker reloads the database record and generates temporary inventory, key, and extra-vars files.
  7. An SSH ping check separates reachable and unreachable targets.
  8. If at least one target remains eligible, the playbook continues for those targets.
  9. Ansible output is streamed, parsed, stored, and exposed as live progress.
  10. The recap is parsed into per-target results.
  11. Django computes the global status and stores timings and diagnostics.
  12. The frontend polling loop displays the final report.

9. Multi-Target and Partial Success

The generated inventory uses the selected_hosts group. Playbooks use Ansible's free strategy so a slow host does not unnecessarily block task progression on healthy hosts.

SituationGlobal result
Every selected target succeeds.success
At least one succeeds and at least one fails or is unreachable.partial_success
No target succeeds.failed
The operator cancels the run.cancelled

A target can therefore fail SSH validation without stopping installation on reachable targets. Each target keeps its own return code and relevant output.

10. Ansible Runner Abstraction

LinuxRunner

Runs ansible and ansible-playbook directly on a native Linux controller.

WslRunner

Converts Windows paths to /mnt/<drive>/... paths and executes Ansible in the configured WSL distribution.

Both runners provide connectivity checks, ad-hoc commands, streaming playbook execution, timing metadata, Ansible configuration variables, and callback activation.

11. Installer, Conflict, and Cleanup Workflows

PlaybookBehavior
k8s_single_node.ymlCommon preparation, containerd, Kubernetes packages, kubeadm initialization, Calico, and validation.
k8s_cleanup.ymlReset cluster state but retain packages for a faster reinstall.
k8s_full_uninstall.ymlRemove cluster state and Kubernetes-managed packages and services.
k3s_single_node.ymlK3s installation, service configuration, kubectl access, and health validation.
k3s_cleanup.ymlRemove K3s service, binaries, state, kubeconfig, and managed interfaces.

K3s and kubeadm Kubernetes must not coexist on the same single-node target. The playbooks detect conflicting artifacts before destructive changes. The serializer converts known conflict messages into an operator action so the UI can offer the correct cleanup workflow.

12. Progress, Timings, and Diagnostics

  • Celery publishes coarse execution steps and live Ansible task metadata.
  • The service parses play, role, task, recap, profile timings, and runner return code.
  • timings stores SSH and playbook duration.
  • task_profile stores slow Ansible tasks.
  • bottleneck_hints explains likely download or rollout delays.
  • Target stdout/stderr is separated so result modals can show relevant output per host.
  • The database remains readable even if the Redis result metadata is temporarily unavailable.

13. Security Model and Honest Boundaries

Current protections

  • Serializer input validation.
  • Controlled playbook paths.
  • No shell interpolation for native Linux runner commands.
  • Generated temporary key files with restricted permissions.
  • Secret redaction from user-facing diagnostics.
  • Ansible no_log for selected sensitive tasks.

Current limitations

  • Credentials are stored in database fields without application-level encryption.
  • Installation.inventory_content currently retains generated inventory content and can therefore retain SSH or become secrets.
  • The API has no application authentication or RBAC.
  • Development defaults disable strict SSH host-key checking.
  • There is no global host lock preventing two separate runs from targeting the same host simultaneously.

LinDeploy is appropriate for controlled labs and workshops. Do not expose it to an untrusted network until authentication, authorization, encrypted secret storage, inventory redaction, HTTPS, audit logging, and host locking are implemented.

16. Current Limits and Roadmap

  1. Add login, RBAC, API permissions, audit trail, and encrypted/external secret storage.
  2. Add host-level execution locking and retry policies.
  3. Add a local artifact repository and OCI registry for offline K3s and Kubernetes.
  4. Add shared multi-node and HA topologies.
  5. Add OpenShift SNO provisioning on KVM/libvirt with Agent-Based Installer and oc-mirror v2.

17. Presentation and Defense FAQ

Why use Django instead of running Ansible directly from React?

Django validates input, protects controlled playbook selection, stores durable history, and provides one execution API. A browser must never receive SSH secrets or execute operating-system commands.

Why use Ansible?

Ansible provides remote SSH orchestration, reusable roles, conditional support for Linux families, handlers, retries, and idempotent modules.

Why use Celery and Redis?

Cluster installation can take many minutes. Celery removes that work from the HTTP request, while Redis transports queued tasks and progress metadata.

What happens if one of three targets is unreachable?

The target is marked failed, but reachable eligible targets continue. The final execution is partial_success if at least one target succeeds.

Does selecting three hosts create a three-node cluster?

No. The current mode creates three independent single-node clusters. Shared cluster topology is a roadmap feature.

How is idempotency achieved?

The backend selects and launches workflows; idempotency is primarily implemented in Ansible through state checks, native modules, conditions, handlers, and safe existing-install detection.

What is the difference between reset and full uninstall?

Kubernetes reset removes cluster state while retaining packages for fast reinstall. Full uninstall also removes Kubernetes packages and services. K3s currently has one optimized full cleanup workflow.

Can K3s and Kubernetes be installed on the same target?

No. LinDeploy intentionally blocks that configuration and proposes cleanup of the conflicting platform.

Is WSL required?

No. WSL is one controller backend. Native Linux is supported through LinuxRunner.

Is LinDeploy production-ready?

Its execution workflows are robust for controlled labs, but the web platform still requires authentication, RBAC, encrypted secrets, HTTPS, audit logging, and host locking before exposure in a production network.

How will offline mode work?

A dedicated mirror server will store verified binaries, packages, manifests, and container images. Targets will install from the LAN instead of repeatedly downloading from the Internet.

How will OpenShift SNO fit the architecture?

The same API, Celery, history, target result, and Ansible layers will orchestrate libvirt, DNS, mirror synchronization, Agent ISO generation, installation monitoring, validation, and teardown.

18. Summary

LinDeploy separates user interaction, durable orchestration state, asynchronous execution, platform-independent runner logic, and Ansible configuration. This separation allows Kubernetes, K3s, future mirror workflows, and OpenShift SNO to reuse the same execution foundation.
